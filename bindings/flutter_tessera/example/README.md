# flutter_tessera example — eight tabletop games

A menu of small tabletop games, each rendered live by the Tessera engine inside
a `TesseraView` (a native platform view). Every game is a `GameController`
(sealed state + sealed action + a pure reducer, see `lib/game.dart`) hosted by
a shared `GameScreen` that plays its scenes idle-gated, routes taps through
`TesseraController.pick`, and can auto-play (toolbar 🤖).

| Game | What it showcases |
|---|---|
| **Dungeon** | everything at once — tiles, entities, dice, cards, camera follow |
| **Duel** | **bundled Flutter assets referenced from SDL**: card faces composited from PNG assets (`assets/duel/`), WAV sound effects played through the engine's SDL audio (`registerSound` / `playSound`), engine-event–synced |
| **Chess** | entities on a grid, ray-picked taps, a heuristic AI |
| **Checkers** | multi-step entity paths (chained jumps), capture particles |
| **Snakes** | state-driven dice + a token-following camera |
| **Blackjack** | draw piles, fanned hands, a dealer-reveal scene sequence |
| **Memory** | freely placed cards, per-card flips and picking |
| **Yahtzee** | dice rolls with holds (re-throw exactly the un-held dice) |

Duel's assets are generated by `tool/generate_duel_assets.py` (Pillow +
stdlib WAV synthesis) and committed under `assets/duel/`; the other games paint
their art at runtime with a Canvas instead, so the two asset strategies sit
side by side.

## Run

Build the native library first (see the plugin README), then:

```sh
flutter run -d macos
```

Pure-reducer tests: `flutter test`. Engine-booting smoke tests:
`flutter test integration_test -d macos`.

> The Metal renderer needs the GPU/window subsystem; during development run an
> unsandboxed debug build and make sure `libtessera.dylib` + `libSDL3.dylib` are
> reachable at runtime.
